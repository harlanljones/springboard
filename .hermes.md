# Hermes project rules — springboard

Hermes: when working in this repo, adopt this behavior. `AGENTS.md` (repo root)
is the operating manual — commands, layout, invariants. This file adds
Hermes-specific conduct; it layers on `AGENTS.md` rather than repeating it.

## Session behavior

- Read `AGENTS.md` before your first code edit in a session; its commands are
  verified, so do not re-derive them.
- Run Hermes here via the repo-root **`./dev`** script: it ensures the
  **`springboard` profile**, prunes irrelevant skills, bootstraps
  `.hermes/skills/`, registers the hooks and trusts the repo, then drops you into
  a session. Subcommands: `./dev setup` (bootstrap only), `./dev doctor` (verify,
  exits non-zero on problems), `./dev -q "prompt"` (one-shot).
- Any change is "done" only after `./scripts/verify.sh` is green — that is
  backend tests, frontend tests + typecheck + lint + build, and the packaged jar
  answering real HTTP. Do not report success on a partial run.
- Work in the milestone order in `docs/ROADMAP.md`; when the user asks for
  something out of order, say where it lands and record it there.

## Skill routing (load with skill_view before the task)

| Task in this repo | Load skill |
|---|---|
| Writing any new feature or bugfix | `test-driven-development` — test first; backend tests in the mirrored package, frontend tests beside the module |
| A bug that isn't immediately obvious (build, proxy, packaging) | `systematic-debugging` — root cause before patching |
| Before committing multi-file changes | `requesting-code-review` |
| Executing an approved multi-task plan | `subagent-driven-development` |
| Validating an unknown design before building it | `spike` — throwaway experiment; findings land in `docs/` |
| Docker/compose work (ROADMAP item 2) | `dockerize-web-app` |
| Metrics about the codebase | `codebase-inspection` |
| PRs, issues, reviews on GitHub | `github` |
| Debugging the JVM or Node side | `node-inspect-debugger` (Node/CDP); for the JVM, start with `./mvnw -Dtest=... test` and `application.yaml` logging |
| Reading a secret | `1password` — never paste credentials into the repo |
| Writing bash in `scripts/` or `~/.hermes/agent-hooks/` | `shell-portability` |
| Substantial autonomous multi-step work | `unlazy` — no stubs, verify before claiming done |
| Authoring/extending a skill | `hermes-agent-skill-authoring` |
| Hermes config/profile questions | `hermes-agent` |

Negative controls — do NOT load a skill for these:

- A one-off question about the API contract ≠ `test-driven-development`; answer
  from `docs/ARCHITECTURE.md` and the code.
- A failing test in existing code ≠ TDD from scratch; reproduce, then
  `systematic-debugging`.
- Re-running `./scripts/verify.sh` (or any documented command) loads nothing —
  it is in `AGENTS.md` verbatim.
- A plain `mv`/`rm` inside this repo needs no skill.
- Word-smithing docs or comments loads nothing.

## Greenfield deviations from the reference exemplar

This repo started with **no commits and no `origin` remote**, which breaks two
assumptions the canonical `hermes-repo-devsetup` exemplar bakes into its hooks:

- `springboard-inject-git-status.sh` matches the checkout by **directory name**
  (`basename == "springboard"`), not by a remote-URL marker — a remote-keyed
  match would silently never fire here.
- The injector gates its walk on `rev-parse --is-inside-work-tree` and reads the
  branch with `symbolic-ref --short HEAD` first, because an unborn HEAD makes
  `rev-parse --abbrev-ref HEAD` print a stray `HEAD` and fail. Smoke-test it from
  a subdirectory too, not just the repo root.

Unlike the `~/dev` devroot profile (a parent of many independent repos, where
each project owns its git), **this repo has its own git-guard**: `git commit`,
`push`, `checkout` and friends are blocked for agents. Read-only git passes.

## Hooks (springboard profile)

Configured in `~/.hermes/profiles/springboard/config.yaml`, scripts in
`~/.hermes/agent-hooks/`:

- `springboard-git-guard.sh` — pre_tool_call on `terminal|execute_code`,
  `fail_closed: true`: blocks mutating git, passes read-only git.
- `springboard-formatter.sh` — post_tool_call on `write_file|patch`: runs the
  repo's own `web/node_modules/.bin/prettier` on edited JS/TS/JSON. Guarded no-op
  before `cd web && bun install`; nothing touches `.java`, `.md`, `.yaml`.
- `springboard-evidence.sh` — post_tool_call on `terminal`: appends one compact
  JSONL line per command to `~/.hermes/agent-hooks/springboard-evidence.jsonl`.
- `springboard-inject-git-status.sh` — pre_llm_call: injects branch + dirty-file
  status when the session cwd is inside this checkout.

First session start may prompt for per-profile hook allowlist consent, or run
`hermes --profile springboard --accept-hooks` once.

## Engineering gates (do these yourself, unprompted)

- `./scripts/verify.sh` green before declaring anything done.
- Never let `web/dist` be committed; it is generated. `web/node_modules`,
  `target/` and `.hermes/skills` are gitignored too.
- No secrets in the repo, ever: no `.env` files with values, no tokens in
  `application.yaml`. Reference env var names only.
- Keep the frontend's toolchain in `web/` (bun + `bun.lock`) and the backend's in
  `pom.xml` + `.mise.toml`; do not add a root-level `package.json`.
